# 構成とテンプレート

## 正本の割当

| 内容                       | 正本の候補                                           | 他の文書の扱い                   |
| -------------------------- | ---------------------------------------------------- | -------------------------------- |
| 期待する業務動作           | 能力ごとの要求仕様                                   | 画面から要求IDで参照             |
| 画面固有の表示・操作・状態 | 画面仕様                                             | 状態別画像と受入条件へ参照       |
| API・データ契約            | 既存OpenAPI・スキーマ、または内部契約                | 契約を転記せずリンク             |
| 共通部品の利用契約         | 共通部品台帳                                         | 各画面・内部仕様から部品IDを参照 |
| 関係データ                 | 一つの機械可読マニフェスト、または各正本のメタデータ | 一覧・逆参照を生成               |
| 実装の現状                 | 対象版のコード・実行証拠                             | 期待仕様への適合を別途確認       |
| 画面画像                   | 対象版・状態付きの証拠ファイル                       | 要求そのものを代替しない         |

以下は独自設計例であり、OpenSpecの必須・標準配置ではない。既存配置がある場合は対応表を作り、移動を最小にする。

```text
specs/
  index.md
  governance.md
  capabilities/<capability>/spec.md
  screens/SCR-001/spec.md
  screens/SCR-001/images/<state>.png
  internals/INT-001.md
  shared/CMP-001.md
  decisions/ADR-001.md
  traceability.json
  generated/screen-index.md
```

OpenSpecを採用済みなら能力の要求正本を既存のspecs配下に置いたまま、画面・内部仕様・共通部品を補助文書として対応付ける。マニフェストは要求本文を含めず、識別子・参照・検証根拠を収録する。generatedは手編集しない。

## IDと機械可読関係

IDは改名後も維持し、削除IDは再利用しない。画面と要求は多対多を許す。IDへのリンクは実ファイルと安定アンカー、またはID解決器で到達できるようにする。パス変更も検証する。

```json
{
  "schema_version": 1,
  "baseline": { "revision": "<commit>", "scope": "main" },
  "entities": [
    { "id": "SCR-001", "kind": "screen", "spec": "screens/SCR-001/spec.md" },
    {
      "id": "REQ-001",
      "kind": "requirement",
      "spec": "capabilities/accounts/spec.md#req-001"
    },
    { "id": "INT-001", "kind": "internal", "spec": "internals/INT-001.md" },
    { "id": "CMP-001", "kind": "component", "spec": "shared/CMP-001.md" },
    {
      "id": "TST-001",
      "kind": "test",
      "source": "tests/account.test.ts",
      "selector": "reject-invalid-email"
    }
  ],
  "relations": [
    { "from": "SCR-001", "type": "exposes", "to": "REQ-001" },
    { "from": "REQ-001", "type": "realized_by", "to": "INT-001" },
    {
      "from": "INT-001",
      "type": "uses",
      "to": "CMP-001",
      "evidence": "declared"
    },
    { "from": "TST-001", "type": "verifies", "to": "REQ-001" }
  ]
}
```

kindごとの必須フィールド、許す関係型と端点kind、ID・アンカーの解決、証拠状態の列挙値をプロジェクトでスキーマ化する。baselineを常に同じ変更のコミット値へ更新すると自己参照になるため、証拠のコミットは取得対象版を使い、文書自体の版はバージョン管理で追う。

## 画面の記入例（架空）

```markdown
# SCR-001 アカウント作成

- Route: /accounts/new
- Role: 管理者
- Status: draft（未検証）
- 要求: [REQ-001](../../capabilities/accounts/spec.md#req-001)
- 内部契約: [INT-001](../../internals/INT-001.md)
- 共通部品: [CMP-001](../../shared/CMP-001.md)

| 状態ID  | 前提             | 画像   | 操作と結果                                 |
| ------- | ---------------- | ------ | ------------------------------------------ |
| STA-001 | 初期表示         | 未取得 | 保存操作は入力検証後に要求REQ-001へ進む    |
| STA-002 | メール形式エラー | 未取得 | フィールドの直下にエラーを表示し送信しない |
| STA-003 | 保存中           | 未取得 | 保存ボタンを無効化し重複送信を防ぐ         |

| 要素ID  | 注釈番号 | 意味       | 共通部品 |
| ------- | -------- | ---------- | -------- |
| ELM-001 | 1        | メール入力 | CMP-001  |

## 受入条件

- Given 管理者が入力画面を開いている
- When 不正な形式のメールを入力して保存する
- Then 保存APIを呼ばず、入力欄にエラーを表示する（REQ-001、TST-001）
```

画像ごとにstate_id、対象コミット・ビルド、取得日時、viewport、テーマ、権限、locale、前提データ、取得方法を添える。機密情報は伏せ、変更された画像を古い証拠と混同しない。画像未取得は未取得と記す。更新対象は影響する状態に絞る。

## 内部契約のテンプレート

- ID、責務、実装パスとシンボル、対応要求
- 入力・出力・型・不変条件、エラーと復旧
- 認可と信頼境界、依存方向、データ所有者
- 副作用、トランザクション、並行処理・キャッシュの条件（該当時）
- 利用する共通関数・部品、選択理由、却下した代替とADR
- 契約テスト、確認した版、未確認点

## 共通関数・部品のテンプレート

- ID、役割、実装パスとシンボル、所有者
- 入出力、props、エラー、副作用、アクセシビリティの契約（該当時）
- 使用すべき条件、使わない条件、最小利用例
- 利用先の逆参照（関係データから生成）
- 宣言／静的検出／テスト確認の別と対象版
- 適合レビュー結果、例外の理由・所有者・解消条件
- 廃止予定、代替部品、移行方針

AI向け入口には「対象画面→要求→内部契約→部品台帳→テスト」の読む順番、既存部品を探す場所、矛盾時の扱い、完了条件を短く記す。
