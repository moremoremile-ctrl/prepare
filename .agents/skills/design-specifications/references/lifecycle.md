# 変更と検証

## 最新性を保つ手順

1. 対象版と変更意図を特定し、現行仕様と変更提案を分ける。
2. 変更するIDから要求・画面状態・内部契約・利用部品・呼出し元・テスト・画像への影響を辿る。関係データにない利用もコード検索で補う。
3. 受入条件と設計判断を変更提案に記し、共通部品の契約に適合するかを確認する。
4. 実装・テスト・補助仕様・関係データを同じ変更単位で更新する。実装を先に観察した場合も、それだけで承認済み要件を上書きしない。
5. 対象ビルドで影響状態の画面画像を取得する。取得不能なら理由を記し、確認済み表示にしない。
6. 機械検証とレビューを行い、変更提案が期待動作を満たすことを確かめる。
7. プロジェクトの採用条件を満たした時点で基準仕様へ反映し、索引と逆参照を再生成する。提案をアーカイブするだけで補助仕様を古いまま残さない。
8. リリース基準、未検証・例外、所有者、次の確認条件を記す。

## OpenSpecとの接続

OpenSpecの固有のCLI・ファイル名・拡張方法は導入版で確認する。この参照はツール非依存の接続方針として使う。

- 既存の能力単位の要求を動作の正本とし、画面一覧に能力と要求IDへのリンクを加える。
- 既存の要求見出し・シナリオ構文を変更せず、IDの付与方法を導入版で検証する。独自メタデータがパーサーで許されると仮定しない。
- 変更提案のスコープに画面状態、内部契約、共通部品、画像とテストの差分を含める。
- 現行specsと変更中の差分が競合したら、AIには対象変更と採用済み基準を明示する。未採用差分を現行仕様と混ぜない。
- 基準仕様の更新・変更の保存終了に合わせ、補助文書と関係も更新する。独自検証はプロジェクトの追加チェックとして明示する。
- 正本を既存構成から移す必要がある場合は、移行対象、参照修正、検証、切替日を定め、二重編集期間を作らない。

## チェックの割当

| 項目         | 機械検証                                 | 人・振る舞いの確認                           |
| ------------ | ---------------------------------------- | -------------------------------------------- |
| IDと参照     | 重複、欠落、kind、ファイル・アンカー存在 | 関係の意味が正しいか                         |
| 状態と画像   | 証拠メタデータ、状態への紐付け           | 正しい状態・内容を撮影したか                 |
| 要求とテスト | 宣言された対応、対象テスト存在・実行結果 | 受入条件を実際にカバーするか                 |
| 共通部品利用 | import・参照と宣言の差分                 | 契約適合、ラッパー、動的利用、不要な独自実装 |
| 変更の反映   | 影響IDに関連する仕様更新・例外の記録     | 内容の同期、設計意図、変更範囲の妥当性       |
| 派生ビュー   | 再生成した差分、再現可能な出力           | 探しやすさ・読める表示                       |

最初のCIはID重複・参照切れ・必須メタデータ・派生ビューの一致から始める。全ての古い仕様を一度にゲート化せず、導入済み範囲と変更対象から適用する。警告と失敗条件を明示し、意味の妥当性を機械検証だけで保証しない。

例外には対象ID、理由、承認責任者、期限または解消イベントを要求する。除外を無制限に広げない。期限超過や未確認を表示するが、経過日数だけで陳腐化を断定しない。

## 段階導入

- 初回：既存資料と実装の棚卸し、正本の割当、代表画面のIDと対応表。
- 次：重要フローの状態・要求・契約・部品の記入、実行証拠とテスト対応。
- 次：索引・利用一覧の生成、参照検証、変更時の更新チェック。
- 継続：契約適合のレビュー、未確認の解消、重複仕様と不要な独自実装の整理。

## 設計の受入条件

- 人が画面画像から対象状態・操作・要求を見つけられる。
- AIが対象要求から内部契約・適切な共通部品・テストへ辿れる。
- 部品変更から影響画面・要求・契約・テストを逆引きできる。
- 提案、採用済み仕様、観察した実装、未検証事項を区別できる。
- 重複する要求本文を更新せず、一つの正本と派生表示を維持できる。
- 仕様と実装の相違をissueとして残し、バグ修正か仕様変更かを責任者が判断できる。
