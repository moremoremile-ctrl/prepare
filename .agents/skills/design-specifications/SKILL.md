# 仕様書設計

日本語を基本に、プロジェクトの用語と言語に合わせて設計する。フォルダ構成だけで終えず、正本の責任範囲、IDと参照、代表画面の記入例、更新手順、検証と段階導入を一組として提示する。

## 1. 根拠と現状を調べる

- 依頼が構成設計か、既存仕様の整理か、実ファイルへの導入かを判定し、依頼された範囲を実行する。
- リポジトリがあればAGENTS.md、既存仕様、ルート定義、画面、共有モジュール、API契約、テスト、CI、仕様管理ツールの設定を調べる。既存のID・配置・形式を尊重する。
- リポジトリがなければフレームワークに依存しない提案と架空の記入例を作る。実在の画面・関数・検証結果として扱わない。
- 入手した資料、対象コミットや版、観察環境、未確認事項を記録する。コードから得た現状、承認済み要件、提案、推測を区別する。
- 対象製品、仕様の利用者、変更の流れのうち設計を左右する不足情報だけ確認する。残りは仮定を明示して進める。

## 2. 正本と対応関係を設計する

構成とフィールドを決めるときは [構成とテンプレート](references/structure.md) を読む。

- 画面IDを人の入口にし、要求ID・状態ID・内部契約ID・共通部品ID・テストIDを安定した参照で結ぶ。画面名やソース行番号を唯一の識別子にしない。
- 画面は複数の能力・要求を参照でき、同じ要求は複数画面から参照できる構造にする。画面単位だけに業務ルールを閉じ込めない。
- 内容ごとに正本を一つ指定する。画面ページは要求を参照し、要求本文を再入力しない。OpenAPIなどの既存契約をそのまま正本にできる場合は内部仕様から参照する。
- 承認済み仕様を期待動作、コードと実画面を現状の根拠、画像を特定版・状態の証拠、一覧と利用集計を派生ビューとして区別する。相違をコード側に合わせて無言で正本化しない。
- 「現在」を対象ブランチ・リリース・コミットで定義し、実装済み基準と次版の変更提案を分離する。日付だけで最新性を主張しない。
- 人向けには画像と状態・動作の表、AI向けには機械可読ID・型付き関係・ソース参照・テスト参照を用意する。双方向の一覧は単一の関係データから生成する。

## 3. 動作と実装判断を記述する

- 画面にルート、利用者、権限、通常・空・読込・失敗状態、入力、イベント、遷移、表示結果を記す。画像の注釈番号を要素IDに結び、画像だけでは判断できない動作を文章で補う。
- 要求は前提・操作・観測結果の受入条件にする。権限、バリデーション、重複操作、非同期競合、エラー回復などを対象に応じて含める。
- 内部仕様には責務と境界、入出力、データ不変条件、認可、エラー契約、依存方向、トランザクションや副作用、設計理由を記す。自明なコードの逐語説明を増やさない。
- 共通部品台帳には用途、契約、利用条件、避ける条件、実装パスとシンボル、利用例、代替、移行先を記す。既存部品で満たせるかを先に評価する。
- 利用状況には宣言された利用、静的検出、実行・テストで確認した利用を分ける。importの存在だけで適切な利用を証明しない。ラッパーや動的呼出しの見落としも記す。
- 独自実装は契約不適合などの理由と代替案を記録する。利用件数だけで品質を評価したり、すべてを無理に共通化したりしない。

## 4. 更新と検証を設計する

更新運用とOpenSpec接続には [変更と検証](references/lifecycle.md) を読む。

- 変更要求から影響する要求・画面・契約・部品・テスト・画像を辿り、同じ変更単位で更新する。承認済みの変更を基準仕様へ反映する条件を明記する。
- CIの機械検証と人の設計レビューを分ける。参照切れやID重複は機械検証、部品選択の妥当性や画面の意味の一致はレビューと振る舞いテストで確認する。
- 不足、仕様と実装の差、未確認、期限付き例外を隠さず示す。全件の「最新保証」ではなく、対象版と確認済み範囲を報告する。
- OpenSpecを使う場合は現プロジェクトの設定・テンプレート・導入版を確認し、既存の要求形式と変更フローを残す。画面索引を追加し、別の要求正本を作らない。CLIや拡張形式の正確な仕様が必要ならローカル資料を優先し、不足時は公式の一次資料を調べる。未確認のコマンドや標準機能を断定しない。

## 5. 小さく導入して確認する

- 代表画面一つと利用する共通部品で、画像→状態→要求→内部契約→部品→ソース→テストを通して記入する。
- 「この画面の動作を変更する」「共通部品の契約を変える」「仕様と実装が食い違う」の三つで影響を追えるか確認する。
- 既存プロジェクトは重要フローから現状を棚卸しし、未確認を残して段階移行する。実装を調べずに全件の適合を宣言しない。
- 完了時は構成、正本の割当、記入済み例、更新フロー、検証項目、導入順、未解決事項を提示する。実ファイルを変更した場合は変更内容と実際に行った確認を報告する。
